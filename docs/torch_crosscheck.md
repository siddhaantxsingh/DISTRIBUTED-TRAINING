# Cross-check against PyTorch (torch.distributed, gloo, CPU)

**Status: VERIFIED on CPU, one 4-vCPU host, 1–4 processes.** No GPU was used. Nothing here says anything about CUDA or NCCL; those checks are scripted for the owner and are BLOCKED here (see [OWNER_ACTIONS.md](OWNER_ACTIONS.md)).

All numbers come from one run of `benchmarks/run_torch_crosscheck.py` on 2026-10-15. Raw files are in `benchmarks/results/2026-10-15/torch/`. The tables are in [torch_crosscheck_tables.md](torch_crosscheck_tables.md), generated by `benchmarks/torch_report.py`.

## How PyTorch was obtained

`download.pytorch.org` is blocked on this machine. Details are in `benchmarks/results/2026-10-15/torch/pypi_wheel_probe.txt`.

1. **PyPI wheel with `--no-deps`: failed.** The wheel is 555 MB. It is a CUDA build: `import torch` stops because `libcublasLt` is missing, and `libtorch_cuda.so` links 13 CUDA libraries (cuBLAS, cuDNN, NCCL and others, about 3 GB of wheels).
2. **Docker Hub `bitnami/pytorch`: not used.** It is 3.0 GB compressed, more than the free disk.
3. **conda-forge CPU build: used.** The conda-forge channel is reachable. A `micromamba` binary was copied out of the Docker Hub image `mambaorg/micromamba:2.3.2`. It installed `pytorch 2.14.1 cpu_generic` with Python 3.12 (a 202 MB download). torch reports CUDA unavailable, gloo available.

CI does not have this block. Its `torch-crosscheck` job installs the CPU wheel from the PyTorch index.

## Method

Every rank runs both implementations side by side (`benchmarks/torch_crosscheck.py`):

- dtrain: its own GPT, DDP or ZeroAdamW, over dtrain's TCP collectives;
- PyTorch: an identical GPT (`dtrain/torch_ref.py`), wrapped in `torch.nn.parallel.DistributedDataParallel` and optionally `torch.distributed.optim.ZeroRedundancyOptimizer`, over a gloo process group.

Both start from the same weights and see the same batch on each rank. Both use AdamW (lr 1e-3, betas 0.9/0.95, eps 1e-8, weight decay 0.1). After each step, rank 0 records the largest absolute difference in averaged gradients, in parameters and in loss. The model has 110k parameters (dim 64, 2 layers, context 32, 4 sequences per rank). Each run lasts 50 steps.

## Results

**Collectives alone.** Both libraries all-reduce identical inputs:

- 2 ranks: results are bit-identical, because a + b = b + a exactly.
- 3 and 4 ranks: 32–44 % of elements differ in the last bit. Both libraries are equally close to the exact sum: within 1 ulp of the largest value (|sum| up to 10: ≤ 1.8e-15 in float64, ≤ 7.2e-7 in float32).

The difference is only the order of the additions.

**DDP.** Gradients match torch DDP:

- float64: to ≤ 1.6e-15;
- float32: to ≤ 1.4e-6.

This holds at 1, 2 and 4 ranks. With 1 rank there is no communication, so these differences come from the model's floating-point kernels (NumPy vs ATen).

Parameters after 50 AdamW steps:

- float64: differ by ≤ 5.4e-14;
- float32: differ by ≤ 2.3e-5.

Most of that comes from the optimizer, not from the gradients. With identical gradients, dtrain's AdamW and `torch.optim.AdamW` already differ by 6.7e-6 (float32) and 5.8e-15 (float64). The two compute the bias correction in a different order (`sqrt(v / b2t)` vs `sqrt(v) / sqrt(b2t)`). The Adam update is very sensitive for gradients near eps: its derivative there is lr/eps = 1e5.

**DDP with plain SGD** (lr 0.1) removes the optimizer effect. The step-1 parameter difference is 1e-17 (float64) and 7e-9 (float32). It then grows about 1e4× over 50 steps, at the same rate in both precisions. Over 50 steps it reaches:

| | 1 rank | 4 ranks |
|---|---|---|
| float64 | 2.2e-16 | 4.2e-13 |
| float32 | 7.9e-7 | 4.1e-4 |

The growth comes from the training dynamics amplifying a rounding-level perturbation, not from a bug. The per-step growth is the same in float64 and float32.

**ZeRO-1 vs `ZeroRedundancyOptimizer`.** Parameters match:

- float64: to ≤ 3.9e-14;
- float32: to ≤ 1.6e-5.

Both shard AdamW state and together hold exactly one copy. The sharding differs:

- dtrain splits the flat parameter buffer evenly, so every rank holds 441,856 B (4 ranks, float64);
- torch assigns whole tensors to ranks, so ranks hold between 422,912 and 458,752 B.

**Checkpoint, exit, resume in new processes** (4 ranks, 20 steps, checkpoint at 10):

- dtrain resumes **bit-identically**, for DDP and ZeRO, in float32 and float64.
- After resume, dtrain and torch still agree to the same level as without a restart (1.3e-14 in float64).
- torch DDP + gloo did **not** resume bit-identically at 4 ranks. The difference is about 5e-16 in float64 after 3 more steps (`torch_resume_bucket_experiment.txt`).
  - At 2 ranks it is bit-identical (test `test_checkpoint_resume_bit_identical_in_both`).
  - Two uninterrupted torch runs are bit-identical to each other.
  - Forcing one DDP bucket per parameter did not remove the difference.
  - The cause is not identified. A likely candidate is torch DDP's first-iteration state (bucket rebuild), which changes the summation order at 4 ranks.

## Throughput (CPU, shared machine)

The model is the float32 GPT from [benchmarks.md](benchmarks.md): 0.8 M parameters, 8 × 64 tokens per rank. There is 1 thread per rank and 3 repeats.

**The machine was heavily shared.** The 1-minute load average was 16–21 on 4 vCPUs during every run. Absolute numbers are therefore far below the 2026-10-13 numbers: dtrain single process 1.5k tokens/s, against 2.6k then. Scaling from 1 to 4 ranks is not measurable under this load: neither implementation scaled.

| ranks | dtrain DDP tokens/s | torch DDP (gloo) tokens/s |
|---|---|---|
| 1 | 1,503 | 4,238 |
| 2 | 1,669 | 3,438 |
| 4 | 1,550 | 4,399 |

torch is 2.1–2.8× faster per step. This is mostly the compute kernels (ATen vs a NumPy autograd), not communication.

All-reduce alone (median of 3, same load):

- **Below 1 MiB:** dtrain's ring has lower latency than gloo. At 1–64 KiB it was 264–359 µs against 520–801 µs (2 ranks), and 1.3–1.7 ms against 6–8 ms (4 ranks).
- **At 4–64 MiB:** mixed. gloo was 15–28 % faster at 16 and 64 MiB on 2 ranks and at 4 and 64 MiB on 4 ranks. dtrain was faster at 4 MiB on 2 ranks and at 16 MiB on 4 ranks.

Under this load these figures are indicative only. They should be re-measured on an idle machine.

## Reproduce

```bash
# interpreter with torch (CPU) + numpy; from the project root
python -m pytest tests/test_torch_crosscheck.py          # 8 tests, ~1.5 min; skipped without torch
python benchmarks/run_torch_crosscheck.py --out benchmarks/results/<date>/torch   # ~60 min on 4 vCPUs
python benchmarks/torch_report.py benchmarks/results/<date>/torch > docs/torch_crosscheck_tables.md
```
